# Phishing Analyzer LoRA

QLoRA adapter for `Qwen2.5-7B-Instruct` that reads an email and emits a structured threat
analysis: phishing/legitimate verdict, threat type, risk level, indicators, and mitigation
recommendations.

**This is a learning project.** It was my first end-to-end fine-tuning run. The technical
work is real, but the evaluation has known methodological problems that I document below
rather than hide. Do not use the numbers in this README as a performance claim, and do not
deploy this adapter as a security control.

---

## Status and honest summary

What this project actually demonstrates:

- A working QLoRA fine-tune of a 7B model for structured JSON output.
- A diagnosed and plausibly-fixed failure mode: the first version of the adapter detected
  link/attachment-based phishing but completely missed social-engineering attacks
  (BEC, invoice fraud, impersonation).
- An eval harness, an error analysis, and a retraining cycle.

What it does **not** demonstrate:

- A validated accuracy figure. The evaluation is contaminated (see below).
- Any advantage over a cheaper baseline. No baselines have been run yet.
- Readiness for real email traffic.

## Training data — read this before trusting any output

The base dataset is
[`nosadaniel/phishing-email-training-dataset`](https://huggingface.co/datasets/nosadaniel/phishing-email-training-dataset)
(~2,544 cleaned rows used here). It is **not** an expert-annotated corpus, and that matters:

- The raw emails come from **CEAS-08**, a spam-challenge corpus from 2008. It is old, English-only,
  and its ham and spam come from different sources — a known setup for models learning
  source artifacts instead of phishing signals.
- Only the binary `label` field (ham/phish) is ground truth from CEAS-08. **Everything else
  — `threat_type`, `risk_level`, `indicators`, `analysis_summary` — was generated by an LLM**
  (the dataset card names `gpt-oss-120b` in one section and `gpt-oss:20b` in the example row;
  the card is internally inconsistent). Generation used temperature 0.7, so the targets are noisy.
- Consequence: **this adapter is a distillation of another model's phishing judgments**, not a
  model trained on expert labels. The threat-type taxonomy (`credential_harvesting`,
  `invoice_fraud`, `urgency_pretext`, `impersonation`, `malicious_attachment`) is that model's
  invention, not an industry standard such as MITRE ATT&CK or the APWG taxonomy.
- Note: the dataset card claims "200 balanced samples" in its Source Data section while the
  actual file is 16.4 MB with row indices in the thousands. I used ~2,544 rows. The discrepancy
  is unresolved.

**Custom augmentation (~210 examples):** synthetic invoice fraud, executive/vendor impersonation,
and hard-negative legitimate emails (e.g. a genuine bank-detail-change request routed through
proper verification channels). These were written specifically to close the gap described below.
They are synthetic, and I generated them myself.

Source data is not redistributed in this repo — see the linked dataset for licensing.

## The detection gap (found, and probably fixed)

An initial evaluation on a stratified 50-example test set found the model detected
`credential_harvesting` (6/6) and `urgency_pretext` reliably, but **completely failed on
`invoice_fraud` (0/6) and `impersonation` (0/7)**.

Diagnosis: CEAS-08 phishing skews heavily toward emails with technical artifacts (suspicious
links, attachments). The model learned to key on those markers rather than on social-engineering
patterns. BEC emails, which typically carry no links and no attachments, sailed straight through.

I believe this diagnosis is correct and it is the most useful thing in this project. The fix
(~210 targeted augmentation examples) moved those categories to full recall on the test set.

---

## Evaluation — and why the numbers are not trustworthy

Post-augmentation results on the 50-example stratified set:

| Category | Recall (raw) | Recall (after eval-harness fix*) |
|---|---|---|
| credential_harvesting | 6/6 | 6/6 |
| urgency_pretext | 3/5 | 5/5 |
| malicious_attachment | 3/6 | 6/6 |
| invoice_fraud | 5/6 | 6/6 |
| impersonation | 5/7 | 7/7 |
| **Overall accuracy** | **0.840 (42/50)** | **1.000 (50/50)** |
| legitimate (specificity) | 20/20 | 20/20 |

\* 8 of the raw "misses" were not classification errors. The model produced the correct
`is_phishing` verdict and the correct `threat_type`, but the JSON had a malformed field
(e.g. `"severity": "22,` instead of `"severity": "2",`) that broke strict `json.loads()`.
Fixed with a regex fallback in the harness, not by retraining. I verified the 8 raw outputs
manually.

### Why you should discount these numbers

**1. The test set was used to drive development.** I measured on these 50 examples, found the
gap, wrote augmentation data targeting exactly the failing categories, retrained, and measured
on *the same 50 examples*. That is fitting to the test set. The 0% → 100% jump does not
establish generalization — it establishes that the augmentation covered this specific set.

**2. Possible generator contamination.** Both the augmentation examples and the BEC/impersonation
items in the test set are synthetic and authored by me/an LLM. The model may have learned
stylistic tells of the generator rather than features of fraud. This is a plausible full
explanation for the jump, and I have not ruled it out.

**3. The sample is far too small for the precision implied.** Wilson 95% confidence intervals:

- 42/50 → roughly **[0.72, 0.92]**
- 50/50 → roughly **[0.93, 1.00]**
- 6/6 in a single category → roughly **[0.61, 1.00]**, i.e. compatible with 61% true recall
- 7/7 in a single category → roughly **[0.65, 1.00]**

Per-category "100% recall" on 6 or 7 items carries essentially no information.

**4. The 1.000 figure depends on my own manual re-reading of failures.** Author-performed
post-hoc verification, in the author's favour, without published raw outputs, is not evidence.
For any pipeline that requires strict JSON, **0.840 is the honest number.**

**5. No baselines.** I have not compared against (a) the base Qwen2.5-7B-Instruct zero-shot with
the same prompt, (b) TF-IDF + logistic regression, or (c) a fine-tuned encoder such as DeBERTa
or ModernBERT. Published work reports classical models in the 97–98% range on comparable email
corpora and fine-tuned DeBERTa around 95% recall — at a tiny fraction of the inference cost of a
7B model. Until baselines are run, it is unknown whether this adapter adds anything at all over
simply prompting the base model.

**6. Train/test disjointness is not verified.** I did not systematically confirm that no
test item overlaps with training data.

### What would fix this

- A fresh held-out set built **after** retraining, from a different source (Nazario corpus,
  APWG samples, real inbox traffic), never inspected during development.
- The three baselines above, published as a table.
- The eval harness and test set published in this repo so the numbers are reproducible.

Until then, treat every figure here as an upper bound obtained under favourable conditions.

## Where this model is actually the right tool

A 7B LLM is not a cost-effective binary phishing classifier — a fine-tuned encoder does that
job in milliseconds on CPU. The reason to use a generative model here is the **structured
analyst report**: named indicators, severity reasoning, and mitigation guidance that a human
can read and act on. That is the intended value of this adapter, not raw classification accuracy.

## How to get started

```python
from unsloth import FastLanguageModel
import torch, json

model, tokenizer = FastLanguageModel.from_pretrained(
    model_name="unsloth/Qwen2.5-7B-Instruct-bnb-4bit",
    max_seq_length=1024,
    load_in_4bit=True,
)
model.load_adapter("./")
FastLanguageModel.for_inference(model)

messages = [
    {"role": "system", "content": "You are an advanced AI security analyst specialized in email threat detection. Analyze the provided email and respond with a JSON object containing: is_phishing, confidence_score, threat_type, risk_level, indicators, mitigation_recommendations, analysis_summary."},
    {"role": "user", "content": "<email text here>"},
]

inputs = tokenizer.apply_chat_template(
    messages, tokenize=True, add_generation_prompt=True, return_tensors="pt"
).to(model.device)

outputs = model.generate(inputs, max_new_tokens=500, do_sample=False)
response = tokenizer.decode(outputs[0][inputs.shape[-1]:], skip_special_tokens=True)
print(response)  # parse defensively — see Limitations
```

**Note:** the training/eval system prompt is not baked into the chat template
(`chat_template.jinja` is the unmodified Qwen2.5 ChatML template). It must be passed explicitly
as shown. Results will differ with a different system prompt.

## Output schema

```json
{
  "is_phishing": true,
  "confidence_score": 0.96,
  "threat_type": "business_email_compromise_invoice_fraud",
  "risk_level": "5",
  "indicators": [
    {"category": "...", "finding": "...", "severity": "4", "explanation": "..."}
  ],
  "mitigation_recommendations": {
    "immediate_actions": ["..."],
    "preventive_measures": ["..."],
    "reporting_guidance": "..."
  },
  "analysis_summary": "..."
}
```

`confidence_score` is model-generated text, not a calibrated probability. It has not been
checked against outcomes and should not be used as a threshold.

## Limitations

- **Evaluation is contaminated** — see the section above. This is the primary limitation.
- **No baselines run.** Value over the un-finetuned base model is unmeasured.
- **English only**, trained on a corpus from 2008. Untested on any other language and on
  modern phishing. Substantial distribution shift is expected on live traffic.
- **Context length 1024 tokens.** Real emails with full headers and HTML bodies exceed this and
  will be silently truncated. Not accounted for in evaluation.
- **JSON output is not guaranteed valid** under greedy decoding. Parse defensively (regex
  fallback or a constrained-decoding library); do not assume `json.loads()` will succeed.
- **Not evaluated against adversarial phishing** designed to evade this specific model.
- **Not a security control.** Do not route real mail through this as a filter.
